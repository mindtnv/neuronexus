# Design

## Context

See `proposal.md` for motivation and scope. Inspection on main at `90dd5de` found:

- `ChatPanel` is reused by `screens/chat.tsx` and `screens/notebook-workspace.tsx`, but owns transcript, draft, stream controller, selected model, and pending action state locally. It cannot simply be mounted a second time in a popup without competing controllers.
- `modules/ai.ts` excludes notebook conversations from the default list. `resolveNotebookScope` and `buildToolRegistry({ notebook: true })` couple source selection and capability selection to `conversations.notebookId`.
- `conversations.notebookId` currently cascades deletion. `messages.mentions` snapshots card labels; the composer also finds decks but treats their selection as deck scope. Search uses the limited local mirror.
- The library PDF reader has selection, annotations, quick cards, and harvest. Its Ask action creates/selects a notebook and routes away using `library-handoff.ts`. `TextChunkReader` has neither selection actions nor marks. The notebook citation viewer uses that text reader and links out to the full reader.
- `notebook_notes` and `notebook_artifacts` require a notebook. The artifact worker in `ai/artifacts.ts` already reads a snapshot of source IDs and can be reused once owner admission, limits, and routes are generalized.
- `ai/provenance.ts` links all created cards to the capped set of passages read in a notebook turn. Global source reads do not create equivalent provenance. The existing preview, atomic confirmation, and backlink UI are useful foundations.
- Tests explicitly pin these old behaviors in `notebook-chat.test.ts`, `chat-mentions.test.ts`, `card-provenance.test.ts`, and `library-handoff.test.ts`. The completed unarchived `expand-chat-knowledge-tools` change preserves a narrow notebook registry; this change supersedes that selection rule, not its ownership or checked-source guarantees.

## Goals / Non-Goals

**Goals:** shared conversation state across presentations; one server-verified context contract; common tools with explicit retrieval scope; standalone source study; backward-readable histories and safe staged deployment.

**Non-goals:** a second chat backend, a new generic knowledge database, silently relaxing strict retrieval, guaranteed background execution after browser disconnect, a curriculum engine, or redesigning FSRS/MCP authorization. Existing domain objects remain the source of truth.

## Decisions

### 1. Separate conversation controller from presentation

Create an authenticated, account-keyed assistant controller/provider at the `AppShellWrapper` lifetime. Move transport ownership, transcript reconstruction, active conversation, draft/attachments, pending context, selected model, and confirmation state out of the route-owned `ChatPanel`. Preserve the existing SSE parser and server turn lock.

`ChatPanel` becomes a shared presentation over that controller. The floating host, mobile full-screen host, and `/chat?thread=<id>` select a presentation; only one interactive transcript/composer for the selected conversation is mounted. The controller holds independent sessions keyed by conversation ID: each has its own in-flight reader, draft, model, context, transcript, generation token, and pending approval. It survives presentation remounts and conversation switches. The notebook uses the same controller and conversation list filter, not another stateful chat instance.

Keep an account-scoped bounded draft map per conversation/new draft. Reuse existing draft persistence behavior and add a versioned typed-context payload; invalid/over-budget persistence retains an in-memory draft with an actionable notice. On account change abort all requests, invalidate asynchronous completions, and clear controller/cache state. Minimize, close-window, route navigation, and conversation switching do not abort; Stop targets a particular conversation. Hidden sessions continue while connected and update per-thread streaming/completed/needs-approval indicators without stealing focus. Never evict a streaming session or one with an unsaved draft/pending approval. Completed transcripts can be released and reloaded from the server.

Allow up to three concurrent turns per authenticated user initially, with server admission plus a consistent client precheck; retain the existing one-turn-per-conversation lock. Reaching the cap returns a structured busy response before inserting a user message and keeps the draft. Release slots on completion, suspension for approval, stop, failure, and disconnect; resume/retry must reacquire one. Preserve the project's single-instance deployment assumption for this in-memory limiter and document the need for shared admission if instances multiply. No response is promised to continue after browser disconnection or reload.

Alternative rejected: place the existing `ChatPanel` in a second portal. Its component-local state, navigation effects, and draft keys would create divergent streams and conversation selection.

### 2. Floating geometry and mobile behavior

At widths >=720 use a non-modal movable/resizable window with an initial approximately 440 x 620 size, clamped to available height and width; 360 x 400 is the preferred minimum when the viewport allows it. Controls include minimize, expand to Chats, close, and reset position. Pointer capture handles drag/resize; keyboard move/resize controls and reset provide alternatives. Store only versioned geometry preferences in a safe local UI preference, clamped after resize/orientation changes. The exact initial dimensions are presentation defaults, not a new product setting.

Below 720 use the available full screen (`dvh` and keyboard/visual-viewport handling) with safe-area padding, focus management, and back/close. Preserve underlying reader/reviewer state. Confirmation dialogs layer above the assistant; study shortcuts ignore assistant input/menu focus. Respect semantic theme tokens, reduced motion, and installed-PWA window-control insets. A global launcher is available on authenticated screens; an object Ask action also opens it.

Alternative rejected: docking a mandatory column. The user explicitly wants a floating window and continued access to the underlying page.

### 3. Typed references and effective turn context

Introduce shared versioned `AssistantObjectRef`, `AssistantContextSnapshot`, and validation schemas in `packages/shared`. The v1 registry covers `card`, `deck`, `source`, `source_passage`, `notebook`, `written_note`, `flashcard_note`, `note_type`, `artifact`, and `conversation`. A quiz is an artifact subtype; source formats share one type. Private objects require owner access; builtin note types reuse existing readable-global rules and never become globally mutable.

A reference contains a discriminant and object ID; passage references add source identity and optional chunk/page/section locator and selected quote. Client labels and quotes are display/input data, never ownership or retrieval authority. Server resolution supplies bounded labels, parent metadata, content/version fingerprints, and canonical app links. A selection is verified against parsed text where possible; otherwise it is visibly a user-supplied excerpt associated with a verified source, not a certified exact quotation.

Initial explicit budgets: at most 16 distinct effective refs per turn, 16 pinned refs per conversation, 200-character historical labels, 4,000-character excerpt per ref, and a 24,000-character aggregate excerpt budget. Deduplicate by type/ID/locator before counting. Reject excess with a structured error and preserve the client draft; never silently drop new typed references. Keep legacy card-mention input's current eight-ID behavior in its adapter. Ordinary message/attachment limits remain independently enforced.

Store pinned references in a `conversation_contexts` relation with conversation/user identity, kind/object identity, bounded snapshot/locator JSON, and stable order. Use generic IDs for polymorphic targets so deleted objects can remain tombstones; the resolver verifies live access every time. The conversation/user FKs cascade, but object deletion does not. Add nullable `messages.context` JSONB holding the immutable effective context and focus/strict policy of each user turn, plus a context version/revision and default policy on the conversation for optimistic context edits. Pending tool records carry the exact applicable context version, policy, and evidence snapshot.

New-object Ask proposes a new conversation with visible pinned context in focus mode; an existing unrelated conversation offers add-to-current or start-new. Merely visiting another route only changes a suggested attachment, never stored pins or policy. Message mentions affect that message and replay; pinning is a separate explicit action. Historical snapshots explain what the user supplied; fresh tool reads validate current access and report edits/deletion. Past context is not recursively expanded or automatically repinned by history compression.

Alternative rejected: derive scope from the currently open route or embed all material into every prompt. Both make replay ambiguous; the latter also defeats token bounds and document retrieval.

### 4. Discoverability, contracts, and durable conversations

Add an owner-scoped `GET /chat/context/search` with bounded `q`, optional type/parent filters, stable per-result identity, limit, and opaque cursor. Search source sections within an explicitly selected source; do not full-scan every passage by default. Use deterministic database title/text search and existing domain reads, not embeddings or the 500-card local mirror. Return typed safe metadata, never content bodies or storage keys. Stale search responses cannot replace a later query or account.

Extend conversation create/detail and PATCH for typed pinned context/revision, stream for typed per-message refs, and regenerate for explicit optional context replacement. Resume obtains its context only from the stored pending action. New typed inputs and legacy scope inputs in the same request are rejected as ambiguous; omission of typed inputs invokes the legacy adapter. Add safe capability metadata to `/ai/status` for context v1 and source study so new clients can disable unsupported controls rather than silently discard refs against an old API.

Default `GET /chat/conversations` returns all owned conversations; add explicit `scope=global` compatibility filtering and typed object filters while preserving `notebookId`. Add stable pagination without removing `{ items }` (new `nextCursor` is additive); new UI walks pages, existing consumers still receive a valid first page. Context labels come from the stored snapshot and safe live availability. Old IDs, `/chat?thread=...`, and notebook thread links remain resolvable.

Backfill existing notebook bindings as pinned notebook context with strict policy without changing IDs. Legacy deck-scope requests also adapt to strict policy; typed mentions default to focus instead. Existing per-turn source subsets were not all persisted: preserve any recoverable message/provenance evidence, never fabricate a historical subset, and require a visible current source selection for an unresolved legacy continuation. New turns always freeze their effective policy and source list. Change the notebook FK to `ON DELETE SET NULL`; deleting a notebook leaves the generic reference unavailable and the conversation intact. Direct conversation deletion and account deletion keep their existing cascades.

Useful indexes: context lookup `(user_id, kind, object_id, conversation_id)`, ordered/unique refs per conversation, and conversation `(user_id, pinned DESC, updated_at DESC, id DESC)` for stable browsing. Search queries first constrain owner; add title/search indexes only where an actual query plan justifies them. No HNSW or embedding schema changes.

### 5. One tool service, independent scope and permission

Compose one deduplicated tool catalog from existing card/SRS, source-read, note, and curated knowledge services. Replace the global/notebook registry split with a resolved turn-context service used by every presentation. Keep source-scoped read aliases for old transcripts, and retain the personal MCP legacy adapter boundary to avoid recursive registration. Changing chat presentation must not alter MCP token scopes or preview semantics.

Resolve immutable effective references and `contextPolicy: 'focus' | 'strict'` before each turn. Focus is the default for new conversations: prioritize mentioned material, permit supplementary general explanation and relevant owned-content retrieval using the existing capability gates, and clearly distinguish outside evidence from attached-source evidence. Web access keeps its existing availability and user-intent rules. A mention is not a request to search the entire account indiscriminately, and additional reads never silently add pins. A book citation is emitted only for verified book passages; model knowledge never acquires a fabricated source link.

Expose a visible Only these materials control. An explicit natural-language request for strict grounding is resolved from the current user instruction before evidence-bearing reads: use a bounded, tool-free structured intent step when needed, publish the selected policy to the client, and require explicit policy selection if intent cannot be resolved. This step cannot mutate data, access other objects, or derive policy from quoted/source content. The model execution loop cannot relax strict policy; switching back to focus is an explicit user change. Persist the policy with the turn and conversation preference so reload and regeneration are deterministic.

In strict mode, notebook context expands to its selected owned membership; explicit empty stays empty. A source/passage ref permits reading only its source, with the selected excerpt distinguished from the rest of the document. A deck ref includes its owned subtree. Explicitly added references union allowed objects. Outside-content retrieval requires visible user context expansion; an Add context action can offer candidates, but tool arguments alone cannot grant access. Account-level safe metadata discovery and previewed management operations remain available. Deleted strict context never falls back to global retrieval; deleted focus context is marked missing and supplementary explanation is labelled accordingly.

Guard all content read paths, including the curated GET adapters, so alternative tool names cannot bypass ownership or a strict source set. General management operations remain available and use owner checks and the explicit target preview independently of retrieval policy. Tool availability still depends on chat/search/embedding configuration. Parsed text uses deterministic reading even if embeddings are unavailable; no ready-only gate is added to ordinary readable-source access.

History construction, continuation, regeneration, and compression consume the stored context. A conversation reference permits bounded slices of the selected conversation, not recursive refs or execution of embedded tool calls. Sources, saved notes, selections, and referenced conversations are untrusted data. Summaries never replace ownership checks, context refs, or pending action records.

Alternative rejected: combine both existing registries verbatim. Duplicate names, notebook-only assumptions, and unrestricted curated readers would make the selected source boundary unreliable.

### 6. Per-card evidence from every source-grounded turn

Create a grounding accumulator for every contextual source read, including direct selections and deterministic curated reads. Extend new card proposals with optional per-card passage IDs and evidence fingerprints. Only passages actually supplied/read and still owned can be selected. The preview shows each card's evidence; persist that mapping with the pending call, validate it again on apply, and insert provenance inside the existing card/confirmation transaction. Source changes that invalidate proposed evidence require a fresh proposal. A user-supplied quote that cannot be anchored produces an explicit source-level/quote-snapshot link, not an invented chunk ID.

For new proposals omit provenance when there is no verified evidence and say so. Never attach the entire accumulator to every new card. Preserve legacy pending calls through their existing capped grounding snapshot when they predate per-card evidence; do not silently rewrite previously approved history. Existing provenance/backlinks remain readable. Extend source-level links with bounded quote/location metadata where a chunk link cannot survive; deleting the source keeps the card and an unavailable-source indication.

Alternative rejected: make only notebook turns eligible for grounding, or auto-link every retrieved passage. Both conflict with source-only study and misleadingly attribute evidence.

### 7. Standalone source study without synthetic notebooks

Keep `sources` and `notebook_sources` as they are. Extend `notebook_notes` and `notebook_artifacts` with an owner-kind discriminant, a nullable live source FK (`ON DELETE SET NULL`), immutable source-origin ID/title snapshot, and nullable notebook ownership. Check constraints require either the legacy notebook owner or a source-origin owner with its historical ID; a deleted live source is a valid retained state, not an ownerless record. `userId` remains the authority after deletion. Existing rows backfill as notebook-owned with unchanged notebook cascades. Shared study services use this discriminated owner for access, quota, state, generation, and preview checks. Keep current notebook routes as wrappers; add matching live-source study routes and user-scoped retained-work routes. Personal MCP consumers retain existing notebook calls; source/retained-work variants reuse transaction-aware services.

Source-origin artifacts snapshot only their source at generation time and reuse `ai/artifacts.ts`, quiz validation/attempts, status polling, and shutdown drain. Preserve one-active-generation admission per owner with transactional serialization; include source origin in quotas and admission queries. The new partial active-source-origin index complements the existing notebook index. Add user/source-origin ordering indexes plus a retained-work listing index. Cancel/delete races and reingestion retain worker ownership/readability checks; deleting a source atomically marks its pending/generating jobs terminal with a safe source-unavailable code. A worker's final commit must revalidate source existence and job state, so late results cannot resurrect a deleted source or overwrite preserved completed work.

Source deletion keeps written notes, completed artifacts/quizzes, attempts, cards, and conversations. Source bytes, parsed chunks, and source-dependent annotation anchors still follow their existing deletion lifecycle; saved note/card excerpts survive in their own snapshots. Completed quizzes remain playable and new attempts can be recorded without the source; regeneration requiring missing content is disabled with an explanation. Deleting the retained note/artifact is a separate explicit action using existing preview/confirmation conventions. Notebook deletion continues deleting notebook-owned notes/artifacts, never source-origin work; detaching only removes membership. Attaching a live source does not move or clone its work.

Add a library Saved study work view and user-scoped direct note/artifact links that do not depend on a live source route, with an optional Source unavailable filter. Retained work also remains in typed `@` search. These views allow reading/editing notes, reading documents, playing quizzes, and explicit deletion; historical source labels are displayed with disabled unavailable-source links. Do not create a synthetic notebook to recover these objects.

Extract a shared `SourceStudyWorkspace`/reader surface from the library screen. Both the library route and a notebook's opened-source view use it; a notebook breadcrumb/return action restores source selection and notebook position. Remove the auto-create-notebook Ask handoff. Add source notes/studio access without requiring permanent side columns; the assistant remains floating. The notebook keeps collection-level overview/notes/studio and its filtered unified chat entry.

For URL/EPUB/text, add selection capture with source/chunk IDs plus text quote selectors and offsets, represented by new source text-mark storage rather than fake PDF page rectangles. Anchor against normalized rendered text with chunk/content hashes; handle selections spanning loaded chunks with a bounded ordered locator list. Preserve quote snapshots and mark unresolvable anchors after reingestion. Share Ask, note, card, and provenance actions with PDF while keeping PDF ink/page storage unchanged. A small inline deck-creation flow in direct card dialogs removes the empty-collection dead end.

Alternative rejected: auto-create a hidden notebook per book. It preserves today's storage constraint at the cost of duplicate ownership, surprising deletion, and redundant collections when sources are combined later.

## Risks / Trade-offs

- [Cross-cutting controller extraction] -> Characterize existing stop/regenerate/approval behavior before moving state; exercise navigation during a live stream with deterministic transport tests and a browser acceptance pass.
- [Mixed legacy/new scope semantics] -> One adapter, explicit typed version, migration fixtures, and tests for absent versus empty selections. Existing source restrictions outrank convenience defaults.
- [Object references become stale] -> Store bounded historical snapshots, verify live ownership on every read, detect content/selection version changes, and show unavailable targets rather than substituting IDs.
- [More common tools increase prompt cost] -> Deduplicate schemas, bound registry descriptions and tool results, preserve usage reporting/compression; do not introduce presentation-specific tools again.
- [Retained source work becomes inaccessible or accidentally cascades] -> Distinguish immutable source origin from the nullable live source, enforce owner-kind constraints, provide library/direct access, and test deletion plus late-worker completion races.
- [Concurrent sessions cross wires or exhaust resources] -> Key every stream callback/draft/approval by account and conversation, admit at most three user turns, retain per-conversation serialization, and test stop/error/limit cleanup across sessions.
- [Focus and strict modes become indistinguishable] -> Persist and display the effective policy, enforce strict boundaries server-side, and label supplementary explanation without inventing source citations.
- [Text selection over Markdown differs from raw text] -> Test normalized rendered-text locators on code/math/multiple chunks; preserve a quote-only fallback visibly when exact mapping is impossible.
- [Old API after rollback cannot interpret context v1] -> Disable new-context execution and retain data; a compatibility-capable API remains necessary for continuing new conversations.

## Migration Plan

1. Add shared contracts and versioned migrations for context relations/snapshots/revisions/policy, the notebook FK deletion action, retained source-origin study rows/constraints/indexes, text marks, and bounded provenance locator snapshots. Use UUIDv7 for persistent IDs. Apply the committed chain to a disposable test database; do not let schema push mask missing migrations.
2. Backfill only live notebook bindings into strict context refs and existing notebook study rows into their legacy owner kind; retain legacy columns/JSON. Do not rewrite historical message content, IDs, reviews, source chunks, or embeddings. Verify pre-migration fixtures, repeated migration application, and retained-data deletion behavior.
3. Deploy the API first with old inputs/routes supported, new context capability metadata, legacy pending-call execution, and all new owner/scope checks. New typed messages against an old API must be blocked in the UI, not sent without context. Modern clients use `/chat/context-v1/conversations` for conversation mutations and streaming/resume/regeneration; legacy `/chat/conversations` routes remain wrappers over the same handlers and admission state. The distinct namespace prevents an older API from accepting a request while ignoring new context fields, even after capability metadata has been cached or during a mixed-version rollout.
4. Deploy the web after the API is healthy. Existing conversations open through the adapter; new conversations use context v1. No production data migration or deployment occurs as part of preparing this change.
5. Roll back the web first if necessary, keeping the upgraded API and schema. Retain new columns/tables and `SET NULL`; old web may not display retained source-origin work but must not destroy it. A full old-API rollback is not a supported live-write configuration for context-v1/retained-work data: before it, drain/cancel jobs and block affected chat/study mutation routes at the deployment ingress or enter maintenance. An old binary cannot enforce new policies merely because capability metadata exists. Restore compatible API behavior before reopening those routes. Do not run a down migration or restore cascades while detached histories/source-origin rows exist.
6. Run strict OpenSpec validation, typecheck, migration-faithful full tests, build, and the real-S3 round-trip gate after the final implementation edit. Verify desktop/tablet/mobile and installed-window behavior with real UI interactions. Update `CLAUDE.md` first and mirror `AGENTS.md`, plus `docs/chat-tools.md` and `docs/mcp.md` where contracts change.

## Acceptance Walkthrough

Use a fresh account: upload a PDF, open it, ask about a selection without a notebook, create the first deck/card with verified provenance, and continue reading. Minimize during streaming, switch to another conversation and send a message, return to the first conversation, and verify both streams and approvals remain isolated. Add the card through `@`, compare focus with Only these materials, and resume a pending approval from the other presentation. Reload and verify history/policies/backlinks. Repeat with a URL/text source and with a source opened inside a notebook. Generate a source-origin quiz/note, later attach the source to a notebook, and verify identity and study data remain unchanged. Delete the source, find the saved work in the library and through `@`, edit its note, and play its quiz with attempt history intact. Finally exercise no-chat/no-embedding states, deleted references, cross-account requests, concurrent-send limits, and mobile keyboard/return-to-reading behavior.

## Follow-up decision: contextual page launches

The user clarified that the floating launcher should follow the active Review card and selected Decks object instead of continuing an unrelated card discussion. Those screens register their active object. The account-scoped provider selects or creates a separate contextual session per object, retaining old transcripts/drafts/in-flight work and preserving explicit Ask's current/new choice. Pending context resolution prevents a stale-context send and ignores late results after another page, account or manual conversation selection. The floating host owns compact conversation/new-chat controls in its titlebar. Initial geometry is clamped only after the actual viewport is measured.
